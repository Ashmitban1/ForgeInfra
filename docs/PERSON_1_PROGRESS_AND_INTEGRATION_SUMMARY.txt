5. ACTUAL PIPELINE AND FILES
======================================================================
DHT11 + simulated fault input
  -> hardware/arduino/factoryos_arduino/factoryos_arduino.ino
  -> newline-delimited USB serial JSON, 9600 baud, about every two seconds
  -> hardware/serial_gateway.py
  -> POST /api/telemetry
  -> backend/schemas/incident.py validation
  -> backend/reliability.py deterministic evaluation
  -> backend/main.py latest state and incident dictionaries
  -> GET APIs consumed by dashboard and investigation tools.

The sketch skips output on invalid DHT readings. The gateway adds schema,
device, source, timestamps, sequence, and fault_is_simulated=true. Device ID is
currently hardcoded RACK-01. Sequence starts from laptop epoch milliseconds
and increments. observed_at is assigned by the laptop when it processes the
serial line, not measured by an Arduino synchronized clock. FastAPI assigns
its own received_at and does not trust the incoming receipt time for output.

Gateway catches malformed JSON/missing-key cases and HTTP request failures.
It waits for the next reading after a POST failure; it does not durably queue
or retry the failed event. Serial-disconnect reconnection is not implemented.
bool(reading['cooling_fault']) assumes proper firmware booleans; arbitrary
string booleans are not safely normalized. General malformed-type handling
and strict gateway validation remain improvement work.

Simulator bypasses Arduino and gateway, posting the same v1 event shape with
source_kind=simulator. Do not present simulator readings as physical readings.

6. EXACT TELEMETRY INPUT CONTRACT (CODE)
======================================================================
POST /api/telemetry
Example only; use fresh timestamps and increasing sequences when replaying:
{
  "schema_version": "1.0",
  "device_id": "RACK-01",
  "source_kind": "arduino_serial",
  "observed_at": "2026-11-07T22:20:48Z",
  "sequence": 1794090048708,
  "temperature_c": 29.4,
  "humidity_pct": 54.0,
  "cooling_fault": true,
  "fault_is_simulated": true
}

TelemetryEvent rules:
- schema_version: literal "1.0", defaults to "1.0".
- device_id: string length 1 through 60.
- source_kind: only "simulator" or "arduino_serial".
- observed_at: datetime; endpoint requires timezone information.
- received_at: optional datetime, not authoritative server receipt time.
- sequence: integer >= 0, required.
- temperature_c: number from -40 through 85, required.
- humidity_pct: number from 0 through 100, required.
- cooling_fault: boolean field, required; Pydantic defaults allow coercion.
- fault_is_simulated: boolean, defaults true.
- Extra input fields are forbidden.

Invalid payload/timezone: HTTP 422. Duplicate/out-of-order sequence: HTTP 409.
Sequence ordering is per (device_id, source_kind), not a global counter.
Do not add CPU/memory or other source kinds without a coordinated schema plan.

7. EXACT READ AND POST RESPONSE SHAPES (CODE)
======================================================================
Implemented endpoints:
GET /health -> {"status":"ok","service":"factoryos-person1"}
POST /api/telemetry -> receipt/alert fields plus telemetry result below.
GET /api/telemetry/latest -> {"devices":[telemetry result, ...]}
GET /api/incidents -> {"incidents":[incident object, ...]}
GET /api/incidents/{incident_id} -> incident object, or HTTP 404.

Telemetry result keys:
  schema_version, device_id,
  hardware: temperature_c, humidity_pct, cooling_fault, fault_is_simulated,
            source_kind, observed_at, received_at, sequence,
  legacy_monitor: status, source_revision, sampled_at,
  expected_status,
  reliability: mismatch, reasons, evidence_quality, observation_age_seconds.

POST additionally returns received=true, incident_id (string or null), and
should_alert (boolean). Latest telemetry does NOT include these three fields.
GET incident does NOT currently include should_alert or received either.

Incident object adds:
  incident_id: "INC-COOLING-001" style ID generated by the server,
  created_at, updated_at, status: "OPEN", severity: "HIGH" or "REVIEW",
  investigation: {
    "status":"PENDING", "agent":"nvidia-nemotron", "tool_calls":[],
    "findings":[], "evidence_ids":[]
  },
  decision_review: {
    "status":"PENDING", "reviewer":"gemini", "recommendation":null
  },
  integrations: {
    "jira_key":null, "jira_url":null, "slack_message_id":null,
    "github_pr_url":null, "solana_tx_signature":null
  }.

Use temperature_c/humidity_pct/observed_at, not the Arduino handoff's old
illustrative temperature/humidity/timestamp names. Use uppercase PENDING,
NORMAL, WARNING, OPEN. The old sample ID DC-007 is not the implemented format.
Copy actual IDs returned by the server rather than inventing them.

8. RELIABILITY, ALERTS, AND INCIDENT LIFECYCLE (CODE)
======================================================================
Current legacy_monitor_stub: WARNING only when temperature_c > 35.
Independent rule: WARNING when cooling_fault=true OR temperature_c > 35.
35 is a demo threshold, not a validated universal data-center safety limit.
Legacy source_revision is "demo-legacy-placeholder-v1"; this is not actual
Northmark code and does not prove a completed modernization workflow.

Reasons:
- stale_hardware_reading when age > 90 seconds.
- future_observation_timestamp when age < -10 seconds.
- legacy_missed_fault when legacy and independent status differ.

PARTIAL explanation resolved from code:
  evidence_quality = "PARTIAL" if ANY reason exists, otherwise "CURRENT".
Thus a fresh, correctly read simulated fault can be PARTIAL purely because of
legacy_missed_fault. This does not establish a DHT sensor failure. The current
label combines discrepancy and freshness; discuss semantics before changing it.

should_alert=true when input is fresh and independent status is WARNING.
Models are not involved. This flag alone does not notify Jira or Slack.
Any nonempty reason list creates/reuses an OPEN incident for that device.
Repeated problematic readings update the same open incident's telemetry.
Initial severity is HIGH for a fresh mismatch, otherwise REVIEW; it is not
recomputed on later updates to that incident.

Important current limitations:
- Healthy readings update latest telemetry but do not close/update the old
  incident; healthy POST returns incident_id=null even if an old incident exists.
- Temperature >35 with no mismatch/freshness issue alerts but creates no incident
  because reasons=[]; consumers must not assume every alert has an incident ID.
- No missing-heartbeat alert: freshness is evaluated only on submitted events.
- Latest state is keyed only by device ID; simulator and Arduino RACK-01 readings
  overwrite the same latest entry and may update the same incident.
- No history/time-window endpoint, durable event log, or immutable evidence
  snapshot exists. Incident telemetry can change while an agent investigates.
- All state, sequences, and IDs reset on backend restart; use one backend
  process for the current demo. Separate laptops have separate incident stores.
